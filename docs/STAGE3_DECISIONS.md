# 阶段 3：首版规则与工程决定

日期：2026-11-08（Asia/Shanghai）。本文件将既有用户要求转为首版可实现、可测试的规则，不是功能完成报告；阶段 4 结果须由实际构建和检查证明，阶段 5 的正式统计、后台提醒及重启恢复仍需实现和真机验证。

| 类型 | 含义 |
| --- | --- |
| 用户明确要求 | 本会话已确认的产品目标和授权；不再次要求用户回答同一问题。 |
| 首版实施决定 | 为执行已授权任务而采用的明确默认值和边界处理，不冒称用户已经对未来所有版本作长期选择。 |

| 待阶段 5 验证 | 系统可行性和发布门槛，不能由规则文本或能力验证包短测替代。 |

用户现要求完成阶段 3／4。阶段 5 已获授权为长时间测试临时仅放宽本应用后台耗电策略；先记录原设置，测试后恢复并核验。用户已要求重启恢复此前开启的监测；长期后台耗电策略等实测后再决定。

此前 Java 验证包在 OriginOS 智能管理下无干预短测失败，临时允许后台高耗电后亮屏短测改善，设置已恢复；详见 [STAGE2_THREAD_RETEST.md](STAGE2_THREAD_RETEST.md)。它不是正式包的长期结论，也不证明统计完整性、锁屏、重启或耗电通过。

手机或连接问题立即报告，沿用当前连接和代理，首次失败不自动重连或循环重试。本阶段文档和本地开发不操作手机；后续测试不得扩展成修改全局电池策略、绕过权限或公开私人数据。

## 一、保留的用户要求

- 北斗七星对应一周，起始完整星图 2–3 秒后进入今天；主动返回总览可停留；没有周一至周四闭合线，指定文案为右下角小字。
- 手动安排本周／下周，按天组织，草稿确认才更新首页；完成／取消柔和改变星光，空计划保持基础亮度；生活灵感和使用情况有独立页面。
- 连续 60 分钟、每应用每日 60 分钟、所选合计每日 180 分钟。所选应用切换接续；离开／锁屏 ≤120 秒保持会话关联但间隔不计，>120 秒重开。
- 连续每会话一次、累计每日一次，同时触发合并；用户可稍后 30 分钟，到期仍使用才提醒；关闭监测取消待发提醒。
- 系统时区；午夜日累计重新计数、连续会话接续；未完成保留原日灰色，不自动结转；手动本地备份。
- 重启后恢复此前开启的监测意图，具体自动恢复能力以真机结果为准。

完整需求编号见 [REQUIREMENTS.md](REQUIREMENTS.md)。下列细化按“首版实施决定”执行。

## 二、计划身份、草稿确认与示例

事项具有稳定 ID；正式计划和草稿分开保存，首页完成操作只改变正式记录。确认草稿时进行以下合并：

| 操作 | 完成状态规则 |
| --- | --- |
| 同 ID、同日、trim 后标题相同 | 从首页当前正式记录取最新 done，不能沿用旧草稿中的过期快照。 |
| 只调整顺序／类别，或再次确认未改内容 | 保留最新 done；首页刚取消完成也不能被旧草稿重新勾回。 |
| 仅增加／删除标题首尾空白 | trim 后相同，保留最新 done；UI 和领域层共用规范化规则。 |
| trim 后标题实际改变 | 重置 done=false；不自动重写内部空格或大小写来猜测含义。 |
| 跨日期移动，包括跨周 | 重置 done=false，即使 ID 和标题未变；同日排序不算跨日期。 |
| 新事项 | 默认未完成；删除／添加在用户确认前不污染首页。 |

首次个人计划为空，不自动展示成用户已有安排。示例须主动进入且显著标识；若允许示例完成／编辑，只改独立示例数据。只有明确加入个人草稿并确认，才能转为个人正式事项。

首版允许编辑本周和下周。历史计划及其原日完成状态保留，不按周自动删除，也不将未完成事项滚入新周；首版不因此新增任意历史／未来周编辑功能。计划按日历日期保存，时区变化更新今天与当前周，不擅自平移既有日期事项。

## 三、备份 v1 与覆盖恢复

v1 备份使用明确格式版本，内容为正式计划、草稿、事项完成状态和设置。设置包括首版相关计划／提醒设置；不包含示例、应用使用记录或日汇总、原始事件、连续会话、系统权限、签名密钥、运行中的服务和待发通知。

恢复采用以下流程：

1. 选择本地文件，先校验格式版本、日期／七天结构、事项字段及 ID、完成状态、设置类型与范围。
2. 展示可理解的预览，包括将恢复的周、事项和设置；此时尚不写入个人数据。
3. 用户取消或校验失败，保持当前数据和已有恢复点不变。
4. 用户明确确认覆盖后，先保存覆盖前数据为“最近一次本地备份”，再原子替换目标数据；若保存恢复点失败，不继续破坏当前内容。
5. 最近一次本地备份可再次预览并恢复；不声称保存了无限历史恢复版本。

备份覆盖是用户主动恢复某份快照，因而可以恢复文件中的 done；它不同于普通草稿确认时保留最新首页 done 的合并。未来加入真实监测后，恢复设置不能覆盖现机的通知去重账本或代替系统授权，也不能声称导入文件就已启动服务。

## 四、阈值、范围变更与去重

三类规则分别有开关，默认 60／60／180 分钟。若首版支持编辑，只接受 1–1440 的整数分钟；这是首版实施约束，不是用户对所有版本阈值范围的长期确认。

日使用量取当前所选应用当天可核实的实际使用区间；改变所选范围后重算合计，包含系统可可靠提供的当天既往使用，不以“从勾选时开始”冒充当天总量。

| 变化 | 首版行为 |
| --- | --- |
| 保存阈值或开关 | 保存本身不发通知，既有会话／日提醒标记不清空。 |
| 改变监测应用集合 | 关闭当前连续会话，取消旧范围待发稍后；下次有效使用建立新会话。 |
| 移除再加入同一应用 | 重新计算可核实的当天量，但保留该应用原日期已提醒标记。 |
| 降低阈值，相关规则尚未提醒 | 在下一次有效使用时判定；不遍历历史应用补发一串超时通知。 |
| 降低阈值，相关规则已提醒 | 原标记继续有效，不因设置保存重复提醒。 |
| 用户停止监测 | 停止当前会话，取消稍后，并将持久“监测启用意图”置为关闭，防止重启自行恢复。 |

去重至少区分连续会话、当地日期＋应用包名的单应用累计、当地日期的所选合计。所选合计不因应用集合变化就生成新的当天通知额度；选择变更不能作为重复通知的入口。既往日期账本保留，往返时区不能通过重置账本重复提醒。

未提醒规则在下一次有效使用时判断；单应用累计只就该次实际使用的应用判定，合计就当前所选范围判定。多个有效原因同时达到时只发一条并记录各原因，不能补发历史洪流。权限不足时不伪造送达，设置界面与诊断须区分可判定、未提交、系统已提交及用户确认可见。

## 五、分屏、数据质量与时间

逐应用采用系统可提供、可确认的 resumed／visible 时间段，并注明所用口径；所选合计和连续有效使用使用区间并集，避免分屏重叠双算。锁屏／离开间隔不计为有效使用。能取得可见或 resumed 事件，不等于知道真实焦点、注意力、内容或使用目的；不新增无障碍、设备管理员或其他敏感权限来猜测。

| 边界 | 首版处理目标 |
| --- | --- |
| 午夜 | 按当前系统 zone 将日累计切分到两天；连续会话接续。 |
| 时区变化 | 重算本地日界线和能核实的当天区间，刷新今天／当前周；持久保留既有日提醒账本，不能仅因 zone 改变清零。 |
| 系统墙钟变化 | 可疑区间保守标记质量；不补造负数、重叠累计或看似完整的时长。 |
| 系统事件缺失／留存不足 | 显示数据不完整，不把不可用伪装为零，也不猜测补齐。 |
| 多次查询同一批事件 | 结果幂等，同一时间段不反复相加。 |

使用统计与系统数字健康可能口径不同，正式界面应说明而不是承诺完全相等。

## 六、稍后与重启恢复

稍后为 30 分钟，用当前启动周期内的单调时间计算截止时刻；记录稳定请求 ID，重复操作替换同一个待发请求。墙钟或时区跳变不改变同一次启动周期的稍后间隔。

发送必须有有效证据证明“计划到期时”和“实际发送时”都仍在使用监测应用。迟到时记录真实延迟，不以实际发送时仍使用推断到期时的状态；事件不足或任一条件不成立，本次不补造／补发，并显示取消、状态不明、延迟或受系统限制的真实状态。确认可发送时至多提交一次，不扩展成无限重复。

单调时间不能跨系统重启直接复用。首版明确取消旧启动周期未完成的稍后请求；重启恢复的是此前监测启用意图，不是复活旧的到期通知。

| 重启前状态／恢复条件 | 目标行为 |
| --- | --- |
| 用户之前已开启监测 | 持久保留意图，恢复前重新检查使用情况权限、通知渠道及后台条件。 |
| 用户之前已停止监测 | 不自动开启，不把“曾经开过”当作当前启用。 |
| 权限或后台条件不足 | 显示等待恢复／需要操作，不显示虚假的运行成功。 |
| 系统允许恢复 | 在系统许可范围尝试恢复；启动成功必须以实际服务状态和推进的心跳验收。 |
| 用户强制停止或系统不允许启动 | 不承诺强行唤醒或绕过限制，说明状态并保留计划功能。 |

能否在目标 OriginOS 自动恢复、锁屏是否及时、启动入口／服务类型的合法可用性以及迟到可接受上限，均须阶段 5 实测。该表是实现目标，不是已经实现的能力。

## 七、工程选择与交付边界

| 项目 | 首版选择／边界 |
| --- | --- |
| 正式界面 | Kotlin／Jetpack Compose。 |
| 正式包名 | `io.github.githuiy.starlive`，与两个验证包独立。 |
| 能力实验 | `org.starlive.probe`、`org.starlive.usagefixture` 继续为 Java 验证工具，不能冒充正式功能。 |
| 数据 | 本地 AtomicFile 保存计划和设置；领域核心为可独立测试的纯 Java，Android 系统能力在适配层实现。 |
| 网络与账号 | 首版本地离线，无账号／网络服务，不请求联网权限，不接广告或行为上传。 |
| 构建 | 暂用 minSdk 26、compileSdk/targetSdk 35；工程配置不代表低版本都已测试。目标验收为现有 Android 15／API 35 真机。 |
| 签名 | 阶段 4 的开发／debug 包不等于正式发行包；长期 Release 签名及覆盖升级后续验收，私钥不入库。 |

验证包的系统授权及后台策略不自动转移到正式包。阶段 5 的临时后台例外须限定实际测试包，并记录与恢复原策略；不能把“允许后台高耗电后短测成功”写成“默认智能管理已修复”或“长期耗电已合格”。

## 八、验收分配与仍未量化事项

阶段 4 本地检查应覆盖：空个人计划／示例隔离、星图与页面导航、草稿隔离、最新 done 合并、改名／跨日重置、历史保留、备份校验／取消／覆盖前恢复点及原子保存失败路径。构建、逻辑检查和可检查的界面结果应另记，不能用本文件代替执行结果。

阶段 5 应覆盖：三类真实提醒、119.999／120.000／120.001 秒边界、区间并集、范围／阈值变更去重、午夜／时区／时钟变化、双时刻稍后条件、权限撤销／恢复、重启恢复意图及实际服务状态。长测应记录统计完整性、提醒延迟／遗漏、锁屏、省电、进程终止、重启和耗电条件。

正式可接受延迟、统计误差、耗电上限和长测时长尚未定量确认，由阶段 5 数据和用户取舍确定。当前不虚构性能通过，不承诺长期后台策略，更不将阶段 3／4 完成等同于完整 APK 已达到正式交付门槛。
