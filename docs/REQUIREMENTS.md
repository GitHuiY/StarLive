# StarLive 需求与首版实施规则

更新日期：2026-11-08（Asia/Shanghai）。来源为项目交接说明及本会话后续确认；后续确认优先于原型演示值。用户要求、首版产品实施决定、工程选择及待验证事项分别标注；首版选择不是用户对所有未来版本的长期承诺。

本文件规定目标行为，不证明功能已经实现。原 Web 基线见 [BASELINE.md](BASELINE.md)，阶段 3 的完整决策与验收口径见 [STAGE3_DECISIONS.md](STAGE3_DECISIONS.md)。阶段 4 实现结果以实际构建与验收记录为准；正式应用的真实统计、后台提醒及重启恢复仍须阶段 5 实现和真机验证。

## 目标与设备

- 面向个人生活的 Android 应用，以北斗七星呈现一周，用手动周计划保留生活安排，并通过应用使用提醒减少无意识刷视频。
- 本会话最终目标为可自用安装、可持续更新的正式签名 APK。公开发布、上架、部署范围变更不由“本地构建”自动授权。
- 目标真机：vivo S17 Pro，设备标识型号 `V2284A`／产品 `PD2284`，OriginOS 5，Android 15／API 35，物理分辨率 1260×2800。
- 固件参考版本：`PD2284B_A_15.2.19.0.W10.V000L1`。首版构建暂用 minSdk 26、compileSdk/targetSdk 35，这是工程选择；目标真机验收仅覆盖 API 35，不能据此宣称其他版本均已验证。

设计保留用户选择权，以周为整体、以天为入口。完成事项给出柔和反馈，计划中也给休息留位置。工作安排由用户手动添加。

## 星图与导航

| ID | 需求 |
| --- | --- |
| UI-01 | 冷启动先展示完整星图约 2–3 秒，再按系统当地日期自动进入今天的星与日计划；不要求先手动点星。 |
| UI-02 | 可以查看其他日期；顶部缩略星图返回全周总览。用户主动回到总览后可以停留，不反复自动放大。 |
| UI-03 | 保留现有七日星图视觉基线，不连接周一与周四；“把日子还给自己”保持右下角小字。 |
| UI-04 | 延续现有映射：周一·天枢、周二·天璇、周三·天玑、周四·天权、周五·玉衡、周六·开阳、周日·摇光。这是原型设计基线。 |
| UI-05 | 每完成一项增强对应星光，取消完成则按比例回退；空计划保持基础亮度，不能伪装成全部完成。动画柔和，支持减少动态效果。 |
| UI-06 | 星图、生活灵感、屏幕使用、周计划各有独立页面；生活灵感和使用情况不能用首页大弹窗替代。真正提醒可用通知或轻量提示。 |
| UI-07 | 小屏和字体放大时主要操作可达，点击范围、返回行为和可访问性状态可理解。 |

## 周计划与本地数据

| ID | 需求 |
| --- | --- |
| PLAN-01 | 第一版安排本周和下周，按天组织，不自动分配每日任务，不强制切成固定分钟格。历史计划保留，不自动清理或结转；首版编辑范围为本周／下周。 |
| PLAN-02 | 新增、编辑、删除先进入草稿，用户确认后才更新首页正式计划；草稿、正式计划与示例数据隔离。 |
| PLAN-03 | 生活灵感是可选建议，可加入指定周／日草稿；用户确认后才显示在正式计划中。支持用户自己输入事项。 |
| PLAN-04 | 未完成事项保留原日期、灰色显示；不自动迁移到下一天或下一周。 |
| PLAN-05 | 使用稳定事项 ID；完成／取消状态重启后保留。首版确认草稿时，以首页当前最新完成状态为准：同 ID、同日期且 trim 后标题未变，排序／类别／重复确认保留状态；trim 后标题改变或跨日期移动则重置未完成。 |
| PLAN-06 | 跟随系统时区；长时间打开时跨午夜、跨周及时刷新日期和对应计划。 |
| PLAN-07 | 提供手动本地导出／导入备份。首版 v1 包含计划、草稿、完成状态及设置，不含示例或使用记录；先校验和预览，用户明确覆盖前保留最近一次本地备份，该备份也可预览恢复。 |

PLAN-05 的合并细则、PLAN-07 的 v1 格式及覆盖恢复流程属于阶段 3 首版实施决定。首次进入个人模式默认为空计划；示例须由用户主动体验并显著标识，完成与编辑均和个人数据隔离。任意历史／未来周编辑不纳入首版；历史保留不等于自动将旧事项移入本周。

仅修改标题首尾空白不算改名，UI 与领域层使用同一 trim 规则。用户在首页取消完成后再确认未改的旧草稿，也不能被旧草稿中的完成快照覆盖。备份覆盖恢复是用户预览后主动恢复快照，与普通草稿确认的合并规则不同。

## 使用统计与三类提醒

### 阈值和作用范围

| ID | 模式 | 已确认阈值 | 范围及正常触发频率 |
| --- | --- | --- | --- |
| REM-01 | 连续使用 | 60 分钟有效使用时间 | 所选监测应用构成一个连续会话；每会话正常提醒一次 |
| REM-02 | 单应用每日累计 | 每个应用相同，60 分钟 | 按包名分别累计；每应用每当地日正常提醒一次 |
| REM-03 | 所选应用每日合计 | 180 分钟 | 所选监测应用的有效使用总量；每当地日正常提醒一次 |

三种模式均需实际实现并各有开关。默认 60／60／180 分钟是用户已确认要求；若首版提供分钟编辑，仅接受 1–1440 的整数，是此次实施约束，不是用户已确认的长期范围。原型的 45 分钟默认值与演示滑块范围不再作为正式规则。

### 会话与计时

| 场景 | 已确认处理 |
| --- | --- |
| 从监测应用 A 切换至监测应用 B | 连续会话接续；分别更新 A／B 的日累计，同时更新所选合计。 |
| 离开监测应用或锁屏后，在 120 秒内返回 | 保持会话关联；**恰好 120 秒也接续**；离开或锁屏期间不增加使用时间。 |
| 离开或锁屏超过 120 秒后返回 | 新建连续会话；旧会话结束在实际停止使用时，不把宽限间隔补为使用时间。 |
| 跨当地午夜 | 日累计按系统时区的新一天重新计数；跨午夜的连续会话接续，不因午夜清零。 |
| 监测关闭 | 停止该监测范围的提醒，取消待发的稍后提醒。 |
| 缺少事件或授权撤销 | 明确显示不可用／不完整；不能把缺失数据展示成确定的零时长，也不能凭空补齐使用区间。 |

“连续”是会话内有效使用时间累计，宽限只保留会话关联，不等于把离开时间计入阈值。统计以包名为稳定应用标识，不能以固定演示应用或显示名称代替。

同一监测时刻不应因多个事件或重复查询而重复累计。阶段 3 定稿的首版实施口径为：逐应用使用系统实际提供、可确认的 resumed／visible 时间段，并在界面注明采用哪种口径；所选合计及连续有效使用按这些时间段的并集计算，分屏重叠部分不重复相加。不能据这些事件断言用户焦点或使用目的，也不为此增加敏感权限；不能宣称与系统数字健康数值完全一致。

### 设置、范围与时间变更（首版实施决定）

- 所选应用日累计合计按当前所选应用当天实际使用重算，包括系统能够可靠提供的当天既往区间；缺失区间显示不完整。保存设置本身不发送提醒。
- 选择范围变化结束当前连续会话，并取消旧范围待发稍后请求；下一次有效使用建立新会话。旧日记录及既有提醒标记保留，不能靠移除／重新选择应用或开关规则重复通知。
- 降低阈值后，尚未提醒的相应规则在下一次有效使用时判定；不逐个补发历史应用的超时通知。已提醒的会话／日期标记不因保存阈值而清空。
- 时区变化后按当前系统 zone 重算本地日界线、显示日期及可核实的日统计，持久保留提醒标记，避免往返时区后重复通知。系统时间变化的可疑区间保守标注质量，不产生负数或重复累计。
- 计划以日历日期保存；时区变化更新“今天”和当前周，不擅自把已保存某日期的计划挪到另一日。

### 通知、合并与稍后

| ID | 需求 |
| --- | --- |
| NOT-01 | 达到阈值后按上述会话／日范围正常通知一次，防止周期查询反复触发。 |
| NOT-02 | 同一判断时刻达到多项条件时，合并为一条提醒，保留相应触发原因并同步记录各条件已提醒，避免随后拆成多条轰炸。 |
| NOT-03 | 通知提供“稍后提醒”；用户选择后延后 30 分钟。首版要求计划到期时与实际发送时均能确认仍在使用监测应用，才发送；使用单调时间计时，避免系统墙钟跳变。 |
| NOT-04 | 关闭监测取消待发稍后提醒；用户主动选择稍后不等于开启无限自动重复，也不重置已触发的阈值标记。 |
| NOT-05 | 通知点击进入相应页面，通知权限拒绝／撤销时说明无法正常送达；不借其他敏感权限绕过。 |
| NOT-06 | 提醒保持温和，不自动封锁应用，不默认引入无障碍、设备管理员或 root。 |

稍后请求使用稳定请求标识，重复选择替换一个待发请求，不创建并行重复通知。迟到时记录实际延迟；不能用后来仍在使用推断到期时也在使用。事件不足或任一时刻不满足时，不补造／补发该次提醒，并展示取消、状态不明或延迟等真实状态。

首版实施决定：单调截止时间只在同一次系统启动中有效；手机重启后取消旧启动周期的未完成稍后请求，不将旧 elapsed 值直接用于新启动周期。重启恢复此前开启的监测是独立需求，不能借此复活旧稍后通知。具体并发、权限及系统行为仍须阶段 5 真机验收。

## Android 权限、隐私与后台边界

- 使用情况拟由 `UsageStatsManager` 提供。用户需要主动在系统使用情况访问页面授权；拒绝统计权限不影响星图和周计划。
- 使用情况权限与通知权限分别管理；返回应用时重新检查授权，支持拒绝、撤销及重新授权。
- 仅统计系统提供的应用使用事件与必要时长，不读取视频、聊天内容或用户目的。
- 首版本地离线、无账号、无网络服务，不请求联网权限；应用使用记录、计划、签名凭据不进入公开源码、示例数据或测试日志。不因能力验证要求上传用户真实使用记录。
- 第一版正式范围围绕本地计划、真实统计和本地提醒；不因“交流思考”事项而接入 AI 服务。新增账号、云同步、聊天或自动排程需要另行决定。
- 后台查询不是系统实时事件推送；不能以普通周期任务或无限轮询承诺秒级送达。前台服务类型、启动限制、通知及电源策略必须在 Android 15 真机核验。
- 目标 vivo 需要覆盖前台、后台、锁屏、省电、进程终止和重启；记录实际延迟、遗漏、持续运行及耗电。后台能力未知时立即报告，不把 ADB 连接或截图成功当成此项通过。
- 提醒误差、可接受延迟及耗电上限尚未量化，先做最小能力验证，再将测量结果和接受范围作为发布门槛。
- 用户已要求手机重启后恢复此前开启的监测。持久保存启用意图；用户主动停止则清除此意图。恢复前重新检查使用情况权限、通知及后台条件，条件不足显示待恢复／需用户操作，不声称运行成功；系统能否自动恢复须阶段 5 在目标真机确认，不承诺强制停止后强行唤醒。

## 正式工程选择（不是功能完成记录）

- 正式应用使用 Kotlin／Jetpack Compose；正式包名 `io.github.githuiy.starlive`，与 `org.starlive.probe` 和 `org.starlive.usagefixture` 独立。验证包已有权限和电池例外不会被当成正式包已经获授权。
- 计划与设置通过 AtomicFile 在本地保存，领域核心采用可独立测试的纯 Java；系统权限、生命周期和通知由 Android 层适配。
- Java 验证包继续用于能力实验，不代表完整正式界面或正式提醒规则；正式 Release 签名和升级验收属于后续阶段。
- 首版备份不包含原始使用事件、日汇总、会话、示例数据、系统权限、签名密钥或运行中的服务状态；导入设置不能替代系统授权，也不覆盖现机的通知去重账本。

## 关键验收样例

| 编号 | 输入／操作 | 预期 |
| --- | --- | --- |
| T-01 | 监测应用 A 使用 35 分钟，再切到 B 使用 25 分钟 | 连续有效使用达 60 分钟；A／B 分别累计，全局不重算同一时间段。 |
| T-02 | 离开或锁屏 119.999 秒、120.000 秒、120.001 秒后返回 | 前两组会话接续，后一组重开；三组间隔均不增加使用量。 |
| T-03 | 有效使用时长处于各阈值前 1 秒、恰好达到、超过 1 秒 | 前者不发；达到时发；之后不因重复查询反复发。 |
| T-04 | 一次使用同时达到连续与单应用日累计阈值，或三项同时达到 | 合并一条提醒，所有对应触发条件均标记，继续查询不拆分补发。 |
| T-05 | 23:30 起有效使用至次日 00:30 | 连续会话累计 60 分钟；两天分别计入 30 分钟日累计。 |
| T-06 | 选择稍后，检查到期与实际发送两个时刻，分别覆盖监测应用、非监测应用／锁屏、事件不足、回调迟到 | 两时刻均有有效证据才发一次；否则如实显示状态，不把晚到当作准时；关闭监测后无待发提醒。 |
| T-07 | 编辑草稿、加入灵感、确认、完成、重启，再确认未改内容 | 草稿隔离，确认后显示，完成状态保留；示例不混入个人计划。 |
| T-08 | 跨日／跨周、改变系统时区，未完成事项仍存在 | 日期与当前周刷新，未完成保留原日灰色，不自动结转；时长不产生负数或重复。 |
| T-09 | 权限拒绝、撤销、恢复；系统通知关闭 | 有明确状态，缺数据不当作零，计划仍可用，通知受限时不伪造送达。 |
| T-10 | 导出 v1 备份再恢复；导入损坏文件或不兼容版本；取消预览 | 只含约定数据；校验／取消不改变现有内容；确认覆盖前保存最近一次本地备份，并可预览恢复。 |
| T-11 | 草稿打开后首页完成／取消；随后排序、改类别、只改首尾空白并确认 | 保留首页最新状态；真正改名或跨日期移动才重置未完成。 |
| T-12 | 首次安装、主动进入／退出示例，再导出备份 | 个人计划默认空；示例不污染个人计划或备份。 |
| T-13 | 修改所选范围或降低阈值，再保存和开始有效使用 | 保存时不发历史洪流；范围变化关闭旧会话／稍后；按新规则判定且保留去重标记。 |
| T-14 | 分屏中两个所选应用各有可确认的重叠时间段 | 单应用按已注明口径统计，所选合计用并集；未知区间不补造。 |
| T-15 | 监测开启／关闭两种状态分别重启；撤销权限后再重启 | 只尝试恢复此前开启的意图；重查权限和后台条件，失败可见；旧稍后请求不复活。 |

## 正式 APK 交付门槛

1. 保留上述已认可交互，通过交接清单 A01–A07 和 B01–B06 对应的界面、统计、通知与目标真机检查。
2. 固定包名、版本、依赖和构建工具版本，提供可复现步骤；通过适当的语法／静态检查、计时边界测试及真机验证。
3. 测试最终签名的 Release 包，包括首次安装、覆盖升级、计划与设置保留、离线行为和权限拒绝路径。
4. 提供 APK、SHA-256 校验值、签名证书指纹、构建／验收记录和已知系统限制；签名私钥与密码不入库，保留持续更新所需的签名身份。
5. 公开发布、远端推送、上架及新增部署范围按用户具体授权执行。

当前用户要求完成阶段 3／4；文档定稿和本地开发无需连接手机。用户另已授权阶段 5 为长时间真机测试临时仅放宽本应用后台耗电策略，并要求重启恢复此前开启的监测。测试前记录原策略，结束后恢复并核验；长期后台策略在延迟和耗电实测后由用户决定，不能把临时例外自动永久化。

遇到问题尤其手机问题需立即报告。连接与工具使用优先沿用当前会话；首次连接失败即报告，不自动重连或循环重试。性能、延迟、耗电及自动恢复能力的发布门槛仍待阶段 5 量化，不能因规则写入文档或短测成功而虚构通过。
