# 阶段 2：监测线程与后台延迟复测

记录日期为 2026-11-08（Asia/Shanghai）。

## 上轮问题

首轮验证在 vivo S17 Pro / OriginOS 5 / Android 15 上读到了真实受控使用事件，通知可见及点击返回也成功。但相邻轮询 30→31 的 elapsedRealtime 间隔达到 230.984 秒，用户确认 30 秒测试稍后通知超过一分钟才出现。上轮结论与证据解释保留在 `STAGE2_RESULTS.md`。

本轮先调整线程和诊断，再在相同设备上复测。不能因主线程被移开就预先认定延迟已解决，也不能将改善单独归因于线程：本轮同时减少了测试期间的调试操作。

## 修订目标

- probe 更新为 0.2-probe / versionCode 2，沿用原 debug 签名和权限；fixture 不更新。
- 系统查询、提醒策略及诊断写入进入专用串行工作队列，UI 和稍后／停止动作避免并发改写策略。
- 服务独占 `service-state.json`，UI 不覆盖这份服务存活证据。
- 记录轮询阶段、计划与实际调度时间、查询耗时、诊断写入耗时、提醒计划到期和实际提交时间。
- 同时记录墙钟、elapsedRealtime、uptime 和设备亮屏／省电／空闲状态，区分休眠与可运行时间内的迟到。
- 继续仅处理独立 fixture，不增加网络、精确闹钟、保持唤醒或省电豁免权限，不改变用户手机电源设置。

`Handler` 使用 uptime 调度，深睡会增加实际执行延迟；elapsedRealtime 包含深睡，uptime 不包含。因此需要结合两个单调时钟，而非只比较墙钟。[Android Handler](https://developer.android.com/reference/android/os/Handler#postDelayed(java.lang.Runnable,%20long))、[SystemClock](https://developer.android.com/reference/android/os/SystemClock)

## 复测方案

1. 本机构建与静态检查完成后，校验 APK 签名及权限。鉴于上轮 ADB 安装无结果，直接沿用用户已接受的手机手动覆盖安装方式。
2. 检查新版版本、原授权、服务会话和专用诊断来源。显式启动监测。
3. 设置一次明确标注的 30 秒测试稍后，保存带新请求 ID 且仍待发的服务基线快照，然后打开 fixture。基线在安排请求后取样，避免把历史稍后通知计为本轮结果。
4. 让 fixture 在亮屏状态保持前台约 180 秒；期间不发 ADB、不打开 Probe、不刷新、不截图、不点击通知。保持原电源条件。
5. 窗口结束后先读取一次服务专用文件，再做界面操作；用最近最多 32 轮记录核对最大空档、查询耗时和稍后提交时间。
6. 请用户单独确认实际看到提醒的时间。系统提交成功与实际可见分开记录。
7. 停止测试监测，确认待发提醒取消并保存最终状态。

临时观察线为：无明显深睡的窗口内，相邻轮询最大间隔不超过 15 秒；30 秒稍后提交不能提前，提交延迟不超过 15 秒；一次请求只提交一次。还须检查覆盖度、尾部陈旧快照及未完成轮询，不能只看平均间隔。这些仅为本轮短时回归观察线，不是正式产品发布承诺。

单次采集入口：`scripts/capture-probe-state.py`。离线分析入口：`scripts/analyze-probe-window.py`。两者无重连或网络重试；证据保存于仓库外的工作区 `.device-debug/`。

## 结果

实现与两轮真机复测已完成。线程及诊断修订通过构建；保持原智能策略的复测失败，临时允许本应用后台耗电的对照窗口通过短时观察线。服务已停止，原智能策略已恢复并通过 UI 选中状态核验。此结果不等于默认条件下后台可靠性已解决。

- probe 0.2-probe / versionCode 2，debug APK 36,739 字节。
- APK SHA-256：`e409241df1d4a2ede4498020f3b823bbfd68e2fb05a92a1bc1a8c85fa9ecca0f`。
- 签名证书与 0.1 相同，权限未增加；用户手动覆盖安装，原使用情况和通知授权保留。
- 离线构建与 probe Lint 成功：17 秒、43 项任务（19 执行／24 最新），无 Error；3 条既有 Warning（备份规则与文本资源化）。
- 两套纯 Java 检查共 78 项通过；分析入口用内存模拟检查正常窗口、尾部卡住、历史通知和缺失环记录，后三者均不会假通过。
- 首个服务独占基线确认 schema 2、`starlive-probe-worker`、服务运行、测试稍后待发；亮屏、省电关闭、设备未空闲。
- 基线 `fixture_complete=false`，因此本轮不能同时宣称统计完整性或准确性通过。事件配对算法保持原样以控制线程复测变量，该问题另行排查。

USB 充电条件下的一次短时成功不等于锁屏、省电、进程终止、重启、全天可靠性或耗电通过。

### 保持原后台策略的第一轮

- 实际无干预窗口约 180.250 秒，窗口内没有 ADB、截图、刷新或返回 Probe；用户确认一直亮屏且未看到提醒。
- 同一进程／同一服务会话的首尾专用文件完全相同；tick_enter_count 与 tick_end_count 都停在 1，终点快照陈旧约 181.278 秒。
- 返回 Probe 后 tick 2 才执行：uptime 回调迟到 172.756 秒，elapsed 回调迟到 172.755 秒，额外深睡估计 0。两次系统查询仅 105／93 ms。
- 稍后请求在预定到期后 151.984 秒才决策；此时测试页已退出，被消费但未发送。它不代表预定到期时用户未在测试页，而是提醒未能及时执行。
- 已记录的 UI 查询分别在运行前、恢复后完成，约 106／96 ms；没有证据支持这两次查询造成长空档，但不能完全排除未保留的其他队列任务、锁等待或系统对进程的处理。
- 结论：本轮短时轮询与稍后提醒未通过；迁到工作线程没有独立解决该手机上的后台停滞。监测和待发请求已停止。

### 用户授权的后台策略对照

只读查看本验证应用的系统电量设置，发现“智能控制后台耗电”原本选中，“允许后台高耗电”未选中。用户明确同意仅对该验证应用临时选择后者、再做同样 180 秒测试，并在结束后恢复原智能策略。

临时策略通过界面 checked 状态核验；同一 0.2 APK、相同阈值、相同设备和无干预方式完成第二轮。恢复后读取 UI，核对 `all_intel=true`、`all_opt=false`，生成 `policy-restored.json`；待恢复标记在验证后移除，避免把已完成授权当作后续改设置的许可。

第二轮最近记录完整覆盖窗口，没有历史请求、尾部卡住或 UI 写入被误算为通过。一次稍后请求的本轮提交数与本轮系统通知数均仅增加 1。采样时均亮屏、未开启系统省电；单调时钟估计的额外深睡合计仅约 2 ms。最长整轮工作约 593 ms；末次诊断写入约 36 ms。

计时页累计在窗口内增加 175.606 秒，但末次数据快照早于窗口终点约 4 秒，且完整性标志仍为 false，本轮不用于验收统计误差。静态复核已确认已知闭合后再收到 PAUSED、重复 PAUSED 及回看区间事件等会造成保守误标；不等于手机真实丢失数据。

## 结论与后续

本轮证据表明：仅移动线程未能解决默认智能后台策略下的停滞；同一版本临时放宽该应用后台耗电策略后，亮屏／USB 充电的三分钟轮询和稍后系统提交达到本次观察线。这支持后台耗电策略对该设备上的提醒有实质影响，但单次对照不能穷尽所有进程冻结、队列或系统调度原因，也不能承诺锁屏和全天可靠。

已完成停止监测与待发请求清理，原“智能控制后台耗电”已恢复。两个测试应用和下载的 APK 保留，便于后续复核；未修改其他应用或全局电源策略，未公开发布。

后续优先修正事件配对的完整性误标，再结合用户明确选择的后台策略开展锁屏、省电、长时间和重启测试。正式应用需要明确显示当前授权／后台条件及数据更新年龄，不能把默认策略下未运行的监测显示为可靠运行。
