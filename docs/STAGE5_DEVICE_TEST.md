# 阶段 5 真机长测方案

目标设备为 vivo S17 Pro / OriginOS 5 / Android 15（API 35），使用 `io.github.githuiy.starlive` 的同一构建。记录 APK 版本、SHA-256、系统版本和时区。本文是测试方案。阶段 2 的 `org.starlive.probe` 在智能后台策略下出现约 173 秒调度迟到，临时允许该验证包后台高耗电后，USB 充电亮屏约 3 分钟的测试通过当轮观察线。阶段 4 原生应用已通过本机检查，真机长测以正式应用包的证据为准。[阶段 2 复测](STAGE2_THREAD_RETEST.md) · [阶段 3 决策](STAGE3_DECISIONS.md) · [阶段 4 结果](STAGE4_RESULTS.md)

## 开始前与取证方式

- 等阶段 5 APK 通过本机构建、测试、权限与签名检查，固定一份产物。若涉及覆盖安装，先保留已有计划的手动备份。沿用当前连接和已验证的手动安装方式，连接首次失败即报告，由用户决定后续动作。
- 记录正式应用的原始监测开关、阈值、选中应用、使用情况访问、通知权限及频道、本应用在 OriginOS 的后台耗电选项。只改本轮所需的测试项。原包权限和后台选项以正式包页面实测为准。
- 使用独立计时页 A 与另一个已安排的离线受控目标 B。电脑或另一设备记录开始、切换、锁屏、返回、通知出现和首次解锁的时刻。若只有 A，可以测同应用累计和连续，跨应用接续与分屏保留待测。
- 使用断开 USB、无无线调试交互、无充电的窗口作为长测证据。每轮仅在起止点采集。观察期间按既定步骤使用或放置手机，避免返回 StarLive、反复查询、录屏和刷新。记录不可避免的触摸、来电、锁屏和解锁。在耗电窗口保持手机平放、锁屏且无人使用。
- 亮屏试验沿用正常锁屏超时。若需触碰受控页防止息屏，记下操作并在各策略轮保持一致。锁屏和耗电轮沿用相同省电开关、网络、通知设置和屏幕条件。出现系统自动省电切换、充电、异常发热、较长亮屏或大量后台活动时，单独标记该轮。
- 尾点先在外部钟记录截止时刻及可见通知和电量，再接线或打开测试界面。若读取或解锁唤醒服务，用服务时间戳剔除截止后的工作。只留本包汇总诊断和受控页事件对照。证据目录使用工作区 `.device-debug/stage5/`，文件按构建、策略和窗口分别保存。

## 推荐执行顺序

| 轮次 | 条件与时间 | 核心操作 |
| --- | --- | --- |
| 安装和冒烟 | 原智能策略，约 10–15 分钟 | 手动安装，先看未授权和授权状态。核对默认 60／60／180 分钟及关闭状态。用受控页做至少一个亮屏 3 分钟零 ADB 窗口，先检查正式应用的服务是否真正推进。 |
| 连续与通知 | 原智能策略，至少一个 45–60 分钟亮屏窗口 | 用临时低阈值核验三类提醒、合并、去重及真实 30 分钟稍后。另一轮做切换、短离开和长离开，避免这些动作干扰稍后的到期条件。 |
| 锁屏和恢复 | 原智能策略，至少一次 2 小时锁屏窗口 | 记录锁屏前 A 的时间，息屏且不充电。回来先进入 A，记录唤醒后多久恢复查询和使用判定。再单测重启、权限撤销及有权限后恢复。 |
| 策略对照 | 同 APK、相同使用脚本和屏幕条件 | 智能策略出现停滞或遗漏时，在授权范围内仅对正式包临时选择“允许后台高耗电”，重复同一失败用例。若需收集放宽策略下的锁屏和耗电数据，在本次约定窗口内采完并立即恢复。 |
| 耗电对照 | 每组建议 6–8 小时，三组尽量用同一时段的独立夜间窗口 | 先做智能策略下监测关闭，再做智能策略下监测开启，最后做临时允许后台高耗电且监测开启。每组起点的电量、温度、网络、用机状态相近。结果受系统噪声影响时，用独立窗口复测。 |

首轮只安排冒烟和一个 45–60 分钟提醒窗口。用户负责手动安装与授权、打开受控页、在首条提醒上点一次稍后并返回、记录稍后提醒第一次出现的时刻。窗口内只需按原锁屏超时保持页面在用。用首轮样本安排后续锁屏、重启和耗电时段，长测开始前告知预计结束时刻。临时例外只持续到已安排的测试截止。临时例外下若发现连接、应用、锁屏恢复或耗电异常，立即报告并结束该轮，按下文恢复原策略。

策略对照使用相同测试脚本和判定线，分别记录窗口内最大调度空档、快照年龄、真实提醒及稍后提交延迟、可见／遗漏／重复数量和使用时长误差。三类合并对照要在可比的本地日累计起点进行，必要时用不同日期。需同日复现稍后延迟时，可让两轮都用新的连续会话触发本轮请求，以免每日去重消除对照样本。

## 功能测试步骤

1. **真实阈值与去重**。在 A 当日本地累计为零、只选 A、三个开关都开启时，把三项临时设为 1 分钟。使用外部计时器标出实际进入 A 与 60 秒的时刻，保持 A 连续前台。检查只出现一条含三项条件的提醒，继续使用至少 3 分钟，检查三项去重均生效。若存在当天的历史累计，记录基线，改用真正无历史的受控目标或分开验证各条件。完成后恢复原设置。60／60／180 是正式默认，低阈值短测属于规则验证。另安排真实默认值确认轮，至少积累 180 分钟有效所选使用量，保留各阈值的实际跨越时刻和提醒计数。仅完成短测时，将默认值持续触发列为待测。
2. **切换、离开、锁屏和分屏**。A 前台 60–90 秒，直接切到同样被选中的 B 60–90 秒，连续会话应接续。回 A 前分别安排一次 75–90 秒离开或锁屏及一次 150–180 秒离开或锁屏。短间隔保持会话且不增加时长，长间隔重开，离开期间均不计数。人工操作留出边界余量，119.999／120.000／120.001 秒的判定交给可控时钟测试。系统确实给出 A 和 B 同时可核实的前台／可见片段时，再做一次约 2–3 分钟分屏，核对各自累计和总时间并集。实机事件不足时记录数据质量，不把未观测的重叠补进结果。
3. **真实 30 分钟稍后**。在一次新阈值通知上选择稍后，记录请求接受时刻与标识。回到 A，并确保在计划到期时和实际提交时都仍在所选应用内。检查到期前零提交、到期后恰好一次，分开记录系统提交与用户看到的时刻。另用独立的真实请求覆盖到期时离开、发送时离开、关闭监测取消。为区分两个时间条件，若不能用手动操作可靠卡住两时刻之间的间隙，交给可控时钟测试，真机只记录能证实的事实。锁屏时未发提醒符合未在使用的条件，仍须核对请求确实被决策或取消。
4. **重启及权限**。用户准备好后实际重启。开启监测组在重启前留一个尚未到期的稍后请求，外部记下关机／首次解锁时刻，首次解锁后保持不打开 StarLive。建议观察 5 分钟，期间只进入 A，并在至少两个预期轮询周期后取证。以新启动周期的恢复来源、前台服务及真实心跳共同证明恢复，并确认旧请求取消、未重复提醒、重启间隔未增加使用量。停止监测后另做重启，观察始终关闭。撤销使用情况或通知／频道后分别检查是否明确提示，按正常系统页面授回后再确认可以恢复。若设备阻止自动启动，记录失败发生在开机广播、启动服务、权限检查还是后续轮询。用户手动打开后的恢复结果单独记录。
5. **当地日界线和使用设置**。单独安排当地午夜前后持续使用 A 的窗口，保留两侧可核实的实际时间，核对连续接续、日累计分割及日提醒标记。调整阈值或所选范围时检查保存本身不补发通知，且选择变化结束旧会话、取消旧稍后。精确午夜分割、时区和墙钟跳变先用可控时钟覆盖，用户手机的时区保持原设置。若需测试真实省电模式或进程被系统终止，另开窗口注明条件。强制停止不能替代系统后台回收，主动恢复也不能计作自动恢复。

Android 默认将应用数据保存在首次解锁后才可访问的位置，正常开机广播与 Direct Boot 需分别看待。Android 15 的开机前台服务限制以及厂商后台限制需要从实机启动证据辨别。[Android Direct Boot](https://developer.android.com/privacy-and-security/direct-boot) · [Android 15 前台服务限制](https://developer.android.com/about/versions/15/behavior-changes-15) · [Android 后台优化](https://developer.android.com/topic/performance/background-optimization)

## 记录与判定

| 指标 | 取证与判断 |
| --- | --- |
| 使用量准确性 | 取首尾每应用、合计、连续有效量差值与外部计时对比，报告误差秒数和完整性。切换、锁屏、分屏时使用带时间戳的实际区间。长窗口平均误差可能掩盖短间隔多计或某个目标漏计。 |
| 调度连续性 | 记录服务来源、版本、boot／run 标识、应有轮询周期、开始和结束计数、快照年龄、最大空档及最慢系统查询。区分稳定亮屏、锁屏与状态切换。连续性以窗口完整覆盖为前提，服务仍存在或末尾有心跳只证明局部。 |
| 深睡和卡顿 | 同一启动周期内用 `ΔelapsedRealtime − ΔuptimeMillis` 估算深睡。深睡时允许后台轮询随休眠推迟。亮屏后仍迟到或 uptime 也有大空档时单独报告。10 秒亮屏轮询可沿用阶段 2 的 15 秒最大间隔作为首轮排查线，阶段 5 发布门槛需结合实测。 |
| 通知及时性 | 分别记录规则真实跨越／稍后计划到期、应用决策、系统提交及用户第一次看见的时间。列预期数、提交数、可见数、遗漏和重复。外部计时不精确时给出范围。系统提交延迟和实际看见的延迟分别计算，用户错过观察点时可见时间记未知。 |
| 重启恢复 | 在首次解锁后、打开 StarLive 前确认新 boot 的服务来源、开始时刻、权限状态和心跳。区分“自动恢复”“等待授权或系统限制”“打开后恢复”。已关闭组无自行启动，旧稍后不复活。 |

使用 `elapsedRealtime` 做同一启动周期内的提醒和间隔对比，使用 `uptimeMillis` 辨别深睡。跨重启依靠启动标识与外部时间轴，不能直接相减两次开机的 elapsed 值。[Android SystemClock](https://developer.android.com/reference/android/os/SystemClock)

阶段 2 的 `capture-probe-state.py`、`analyze-probe-window.py` 和 `restore-probe-policy.py` 面向 Probe 的包名、数据结构和短窗口。正式应用需单独核对诊断路径与字段。若只有最近 32 轮诊断，按亮屏 10 秒约覆盖 5 分钟，锁屏 60 秒约覆盖 32 分钟。长窗需要完整的按 run 汇总或独立时间覆盖记录，至少有进入和完成计数、最长间隔、两端时间及未完成轮询。首尾快照只含尾部环时，只能确认覆盖内的事实。先核对结束样本是否陈旧以及是否混入读取、接线或打开应用后的回调。

## 耗电可测范围

- **最低干预**。各轮使用同样的外部计时方式，记录起止电量整数百分比、时长、温度或异常热感、是否充电、锁屏时间、省电状态、信号与明显后台活动。开始时避开刚拔掉快充和高／低电量极端区间。可以提前拔线放置约 15 分钟，在相似电量区间开始。异常升温、手机需用、开始充电或电量降至事先约定的下限就停止。
- **报告方法**。列原始电量读数与每小时下降百分点。用同样时长和条件比较“开监测 − 关监测”和“临时放宽 − 智能开启”。整数百分比有量化和系统平滑影响，一格差异只记趋势。若智能组掉电较少但监测停滞，应与工作完成量及遗漏并列，避免将不同服务可用性当成同等耗电。一次每组只得到探索性对照，长期开启取舍还需看重复观察的一致性。
- **端点细测**。手机和既有诊断入口能提供有效且可比的 `BATTERY_PROPERTY_CHARGE_COUNTER` 时，记录两端 µAh 差，除以 1000 得本机整机估算 mAh。能量计数有效时同理报告整机能量差。属性缺失、为不支持的哨兵值、计数不稳定、或接线后才取得读数时，报告限制或仅用整数电量。单点电流无法代表整夜耗电，端点差也无法直接归到 StarLive。[Android BatteryManager](https://developer.android.com/reference/android/os/BatteryManager)
- **应用级补充**。若本机系统页面给出本应用估计耗电，可同时记录它的统计区间及单位。有既有连接且能限定输出时，应用 UID 的系统估算可用来排查，不把从上次充电起累计的系统估算与本轮实测混用。避免清空系统电池统计、伪造拔线状态或收集全量诊断。若只有整数电量，阶段 5 可以给出整机粗测与可见性结果，精确应用 mAh 仍未知。[Android dumpsys](https://developer.android.com/tools/dumpsys)

## 临时后台策略的恢复

1. 修改前核对页面属于正式包，记录实际选中项、开始时间及计划结束时间。原来为智能控制时按该值恢复，原来为其他值时恢复实际原值。每次临时窗口建立独立待恢复记录。
2. 无论结果通过、失败、提前终止还是连接中断，先记录终点，停止本轮监测及待发提醒，然后恢复原选项。若无法继续连接，立即报告并由用户在正式包的系统页面手动恢复。恢复成功以选中状态复核为准，单独记下恢复时间和状态，核验后关闭待恢复记录，再分析证据。测试用阈值和应用选择随后恢复为原值。
3. 汇总智能与临时策略下的准确性、可见提醒、时延、遗漏、重启恢复和耗电。临时例外结束后维持原策略。长期电池选项由用户根据这份对照决定。
